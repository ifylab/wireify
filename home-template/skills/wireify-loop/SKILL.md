# The Wireify loop

You are co-developing on a **live Grasshopper canvas**. The `wireify` MCP server is your hands on that canvas: it sees the real document, the real components, and -- critically -- the **real data flowing on the wires**. Turn intent into a working, typed Python component on that canvas, and **let the canvas correct you** rather than guessing.

## What is loaded with you

This home ships two knowledge skills (composed by skillmeld -- see `PROVENANCE.md`). Lean on them; do not restate them:

- **`scripting-reference`** -- the deep Rhino/Grasshopper Python API cookbook (rhinoscriptsyntax, RhinoCommon, ghpythonlib): curves, surfaces, meshes, Breps, transforms, analysis. Reach for it when you need *how-to code or which-API*.
- **`rhino-grasshopper-dev`** -- GH development workflow, conventions, input validation, GUID/public-surface preservation, packaging. Reach for it for dev/build/deploy questions and its validation discipline.

**One override:** where those skills describe live automation through the community **RhinoMCP** server or `run_python`, that does **not** apply here. In a Wireify home, **all live canvas automation goes through the `wireify` MCP tools** (listed at the end) -- different tools, same job.

## Two rules above all

1. **Never guess the data. Read it.** `read_input_data` reports the exact types, data-tree shape, and sample values on the wire. Type the script to *that*, not to what you assume.
2. **Never guess the runtime idioms.** CPython 3 and IronPython 2 are different languages. Mixing them is the most common way AI-written Grasshopper Python fails. Pick one per component and stay inside its rules (below).

## Data questions -- answer, do not build

Not every request is a component. If the user asks for **information** -- values, a JSON dump, "what is on this wire", a summary -- the whole job is: resolve the component, `read_input_data` on the relevant inputs (raise `maxPerBranch`/`maxTotal` to cover the tree -- check `tree.dataCount` and read again if the first caps truncated; the reads may go batched in one message), and **answer directly in chat**. For a staged socket, `get_document_summary(includeStagedData: true)` often answers in one call. No component, no `convert_staged`, no reference-skill excursions. One or two batched reads and a formatted answer is the correct shape of that session.

**Orient before you ask.** In this home, vague nouns ("the lines", "the tags", "the points") refer to the live canvas by default. When a request is ambiguous, spend ONE `get_document_summary(includeStagedData: true)` FIRST -- the canvas usually disambiguates (staged input names, wired data, W-numbers). Ask a clarifying question only if the canvas does not resolve it. Never open with a clarifying question you could have answered by looking.

**Budget rule for every request:** orientation plus reads should be under ~6 tool calls. If you catch yourself searching skill references or the install folder to figure out *what to do next* (rather than a specific API signature), stop -- re-read this skill's loop order and act, or tell the user plainly what is blocking. Burning tool calls on meta-investigation is the failure mode; the canvas is right there.

## Numbered sockets -- the primary flow

The user stages work on **Wireify sockets**: Merge-like components with a number badge (`W1`, `W2`, ...) whose inputs they wire and rename on the canvas. "do #3: cull panels below min_area" means socket 3. The built component keeps the staged input names forever — when they are still generic (`in1`, `in2`) and meaningful names would matter, suggest the user rename the socket inputs on canvas BEFORE converting (a rename after conversion is not supported).

1. **Resolve the number AND read the data in one call.** `get_document_summary` with `includeStagedData: true` returns the `wireify` block -- each socket (`staged`, with its staged input names) and each converted component (`converted`), with ids -- plus the live data on every wired staged input (read_input_data shape, default caps). Never guess ids; resolve `#n` here. That one call is normally the whole orientation.
2. **Deeper reads only when needed.** Call `read_input_data` directly only when the inlined samples truncated something you must see (raise `maxPerBranch`/`maxTotal`). Read-only calls may be batched in one message -- they serialize safely on Rhino's UI thread in milliseconds. Never batch a mutation with anything.
3. **Write plain script-mode Python** that reads the staged input names as variables and assigns every output you will declare. No `RunScript`, no class -- top-level statements. The params are built for you; the script just uses them.
4. **`convert_staged`** (socket id, code, `outputs`, optional `inputs`, optional kebab `nicknameSlug`). Pick the slug for the socket's REAL task even when converting with probe outputs first -- the nickname is not re-editable later ("W2 probe-schema" is forever). Params are built EXPLICITLY -- nothing is parsed from your code:
   - `outputs` (required): `[{name, access}]` in order, e.g. `[{"name": "points", "access": "list"}, {"name": "labels", "access": "list"}]`. Access: a single value -> `item`, a sequence -> `list`, branch-structured -> `tree`. A list assigned to an `item` output wraps into one opaque goo -- size access to what the script produces.
   - `inputs` (optional): access (+ optional type hint) per WIRED staged name, chosen from what `read_input_data` showed, e.g. `[{"name": "in1", "access": "list"}, {"name": "in2", "access": "list"}]`. Omit entirely for all wired inputs at tree access. An UNWIRED staged input (the socket's spare default) is dropped from the built component unless you declare it explicitly -- every drop is named in the result's `warnings`, so nothing rides along as a dead param. Un-hinted inputs auto-select a hint from the wired data when one mappable type flows; a mixed-type input gets no hint and the result carries a warning -- relay it before building on that input.
   It swaps the socket for a stock Python component in place -- wires migrated onto the same-named inputs, `W<n>` nickname kept, one undo step, solved -- **and the result carries that first solve's runtime report** (messages + output values). A refusal means your specs did not line up (it says exactly what) and NOTHING changed: fix the arguments, call again.
5. **Read the report you already have.** The convert result's `report` is the post-solve truth -- no `read_runtime_errors` call needed. Red? Fix with `set_source` (it recompiles, solves, and returns the next report in the same call; use `set_io` if the I/O itself must change).
6. **Leash -- any tool, not just convert:** two failed calls of the SAME tool in a row -> STOP. Report the tool's exact error text to the user verbatim and ask how to proceed. Do not iterate script shapes, switch to other components, or search references hoping the third try lands. The server enforces this mechanically for mutations: from the second consecutive failed mutation on a component the error carries a `LEASH:` line -- that line is the stop signal, not a suggestion.

**Revising** a converted component ("revise #3: ...") is ONE `set_source` call in place on the resolved id -- it recompiles, solves, and returns the runtime report with fresh outputs, so a normal revise is a single mutation with its verification built in. Never create a new component or another socket for a revision. Keep the `W<n> ` nickname prefix if you rename anything; the number is how the user addresses it. **If the call refuses with `WIREIFY_EXTERNAL_EDIT`,** the user hand-edited that component's code outside this session (the GH script editor) -- the error embeds their CURRENT code: read it, merge your change into THEIRS (their edits win where they conflict), get the user's explicit OK, and call `set_source` again with `overwriteExternalEdits: true`. The flag is required for ANY write while the component holds hand-edited code -- a correct merge included (the guard cannot verify merges; it re-arms after your write re-stamps). Never pass the flag without the user's OK: on an unmerged write it discards their edits.

Only when there is **no socket** for the task (the user asks in prose, or wants an unstaged helper) use the from-scratch path in the loop below (`create_python_component` + `set_typed_io` + `set_source` + `wire`).

## The loop -- always this order

1. **Orient.** Make sure this definition's lessons are in context: newer homes import `MEMORY.md` straight into `CLAUDE.md` (you already have it); if not imported, Read `MEMORY.md` at the home root first (it is a DIFFERENT file from Claude Code's own auto-memory, which stays empty here). Then ONE `get_document_summary` -- with `includeStagedData: true` when the task names a socket -- plus, only as needed, `introspect_selected` / `get_runtime_info` (these read-only calls may be batched in one message). On a very large canvas the components list caps at 300 (`componentsTruncated: true`; the `wireify` registry is always complete) -- narrow with `nameFilter` instead of re-listing. **This session is bound to ONE definition** -- the summary names it (`activeFilePath`) and says whether it is the front canvas (`isActiveCanvas`). With several files open in Rhino, every wireify tool touches only this session's definition; if the user's request clearly points at a DIFFERENT open file, say so plainly -- they should Connect from that file's socket (each definition gets its own session with its own memory) -- never try to reach it from here. `isActiveCanvas: false` is NOT a blocker: reads route to your definition wherever its tab sits, so keep orienting and investigating freely -- only mutations need it front, and the user only needs to switch tabs at the moment you are ready to change something.
2. **Deeper reads only if the inlined data truncated.** `read_input_data` with raised caps on the specific inputs (or the upstream outputs you will consume). Decide item/list/tree access and the Python types from real data, never assumption.
3. **Build, typed.** Socket staged? -> `convert_staged` (the whole build in one step, above -- returns the first solve's report). From scratch? -> `create_python_component` (`runtime`, default `cpython3`) -> **`set_io`** (declare inputs + outputs explicitly: name, access, optional hint -- plain script-mode NEVER derives params from source) -> `set_source` (plain top-level Python reading those names; it auto-prepends `#! python 3` on CPython 3 -- do not add it yourself; never add it for IronPython 2). `set_typed_io` is SDK-mode only (syncs params from a `RunScript` signature) -- do not use it on plain scripts.
4. **Wire.** Socket conversions arrive wired. Otherwise `wire` the upstream outputs into your new inputs (and outputs downstream where useful). **Reuse check, mandatory:** before wiring into ANY existing component, introspect it and read the target input's `sources` and the output's `recipients` -- a component that looks spare may be load-bearing, and ledger/memory claims about wiring go stale between sessions (a canvas changes between sessions; only the live read is current). An occupied input REFUSES without an explicit mode: choose `replace` (swap the old wire out, one undo) vs `add` (merge -- branches combine) deliberately, and name that choice in the plan you state to the user.
5. **Read the report the mutation returned.** `convert_staged`, `set_source`, and `run` all return the post-solve runtime report (messages + fresh outputs) -- that is your verification, already in hand. If red, diagnose and `set_source` again (idempotent -- reuse the same component); each fix returns its own report. Let the actual error drive the fix. Report outputs are shaped like `read_input_data` -- tree `{pathCount, dataCount}`, a type histogram, and capped samples each carrying its full `valueLength` -- so tree preservation is checkable from the report itself (input 4 branches / 312 items -> output 4 branches / 312 items) with zero extra calls.
6. **`run` and `read_runtime_errors` are for the exceptions.** `run` (a background Task -- poll it, cancel a runaway) when you skipped the inline solve (`solve: false` on a heavy canvas) or must re-solve without a source change -- it RE-SOLVES, so it gates like a mutation (front canvas required), and `runCount: -1` on a native component or param just means no run counter exists there. `read_runtime_errors` reads current messages AND output values WITHOUT solving -- it works from a background tab and on native components and floating params too (a leaf param reports itself as its single output), so it is the way to get ground-truth values off a native leaf (e.g. for an old-vs-new port diff) or anything you must not re-solve; `includeDocument` sweeps canvas-wide messages.
7. **Record the lesson.** Append what broke + what fixed it to this project's `MEMORY.md` as a dated entry in the ledger's own format (`### YYYY-MM-DD [W<n>] title` + Symptom / Cause / Fix / Applies-when -- the rules sit at the top of that file; newest entry on top). At or over the ledger budget (the usage line in its header): consolidate FIRST -- the `wireify-retro` skill is the guided pass (merge near-duplicates, move cross-file rules to `~/.ify/wireify/defaults.md`) -- then append. Each `.gh` compounds its own knowledge. Promotion test: would the lesson hold in a brand-new `.gh`? Yes -> append ONE line to the `## Promoted lessons` section of `~/.ify/wireify/defaults.md` suffixed `(from <home>, YYYY-MM-DD)` and keep only the definition-specific residue here (that write sits outside this home, so Claude Code asks once -- the prompt IS the review gate). A reusable multi-step procedure -> author a skill folder under this home's `.claude/skills/` (it survives Connects); wanted in every definition -> propose `~/.ify/wireify/skills/`.

Keep mutations tight and sequential -- one mutation, read its report, then the next; never batch mutations or mix a mutation with reads in one message. Read-only calls may be batched together (the server serializes them safely). Do not batch speculative changes.

**Reading server errors.** A failed wireify call reports `<tool> failed -- <ExceptionType>: <message>` -- the real cause, read it literally. Server errors carry stable `WIREIFY_*` codes with their recovery protocol in the message -- key on the code, never on phrasing:

- `WIREIFY_BUSY` / `WIREIFY_QUEUE_TIMEOUT` (or "rebuild did not finish"): Rhino is momentarily blocked or the script engine is wedged; the call did NOT run (or did not compile). Wait a few seconds for Rhino to go idle, retry ONCE; if it fails again report the exact error and stop -- never hammer retries. If rebuilds keep timing out, tell the user a Rhino restart clears a wedged engine -- and set the expectation plainly: a Rhino restart ends this session's server, so they re-Connect from Rhino afterwards (memory and logs persist; this conversation does not carry over).
- A bare `"An error occurred invoking '<tool>'."` with NO detail after the tool name is an escaped low-level failure, not the normal error shape (named errors read `<tool> failed -- <Type>: <message>`, sometimes behind that same prefix). Triage with the session log (`~/.ify/wireify/logs/session-*.log`) FIRST: every call that reaches Wireify writes a `→ <tool>` entry line. **No entry line for the failed call = it never reached Wireify** -- the usual cause is a client-side schema/parameter mismatch (a wrong param name or shape from a stale assumption); re-fetch the tool's schema and re-call correctly before suspecting the engine. Entry line present with no outcome = a real wedge: retry ONCE, then stop and report.
- `WIREIFY_NOT_FOUND`: the id is stale (convert_staged replaces the socket's id; undo mints new ids). The error itself carries the current W-registry -- take the right id from there; re-orient with `get_document_summary` only if it is not listed.
- `WIREIFY_INPUT_WIRED`: the target input already has sources and the wire refused; the document is untouched. Decide deliberately -- `replace` swaps the existing wire(s) out (one undo restores them), `add` merges (branches combine) -- state the choice to the user, then re-call with that mode. Never dodge the refusal by wiring into a different input.
- `WIREIFY_EXTERNAL_EDIT`: set_source refused because the component's code was hand-edited outside Wireify since the last write; the document is untouched and the error embeds the current code. Merge your change into theirs, get the user's OK, and call again WITH `overwriteExternalEdits: true` -- the guard refuses every write while hand-edited code sits on the component, merged or not, so the flag is mandatory once you intend to write. Without the user's OK, never.
- `WIREIFY_DOC_NOT_ACTIVE`: this session's definition is open but not the front tab -- mutations only run on the canvas the user is looking at, and the document is untouched. Reads still work: keep orienting and investigating, and ask the user to bring the named file to front only when you are ready to mutate, then re-call. NEVER dodge it by retargeting components on whatever canvas is in front.
- `WIREIFY_DOC_NOT_OPEN`: this session's definition is no longer open in Rhino. Stop -- this session never touches another file; ask the user to reopen it, or to Connect from the definition they mean to work on.
- `WIREIFY_NO_DOC` / `WIREIFY_NOT_A_SOCKET`: follow the recovery line inside the message.
- A `LEASH:` line appended to a mutation error is authoritative: stop immediately, report the exact message verbatim, and ask how to proceed.
- "is not a component" / "No input 'x'" / "not Wireify-managed": your arguments named the wrong object -- re-orient with `get_document_summary`, do not retry blind.
- Anything else: treat the message as ground truth and report it verbatim if you cannot act on it.

## Canvas etiquette

The canvas is the user's live document, not a scratchpad.

- **Never create components as diagnostics.** Isolating a failure never requires a throwaway component -- the error text (it names the real exception) and the read-only tools carry the diagnosis. Any mutation the user did not ask for needs their explicit OK first.
- **Need real values the capped samples cannot show** (plane origins/axes, exact coordinates)? `print()` them in the script for one solve -- the report's `out` output carries the stdout -- then remove the print line. Live-proven for root-causing geometry (per-item plane rotations the "w=1,h=1.2"-style samples never reveal); still zero canvas components.
- **Cleanup:** `delete_component` removes a Wireify socket or a script component -- one undo step, wires restored by ctrl-Z; it refuses everything else. Use it for components created here that the user no longer wants, and confirm before deleting anything you did not create this session.
- **`set_panel_text` overwrites user content** (one undo step). Confirm before writing into any panel you did not just ask to repurpose -- panels often hold the user's own notes or data.
- **No huge literals in tool arguments** (`set_panel_text` included): never generate a multi-thousand-character string as a tool parameter -- producing it is slow and reads as a hang to the user. Big content is created in-script (or the user pastes it in the GH UI); tool args stay short -- paths, code, names.

## Reading wired inputs (the edge)

`read_input_data` returns the payload below per input; `get_document_summary(includeStagedData: true)` inlines the same payload for every wired staged-socket input, so a socket task rarely needs the standalone reads:

```json
{ "param": "x", "access": "tree",
  "tree": { "pathCount": 4, "dataCount": 312, "isFlat": false },
  "types": [ {"typeName": "Number", "clr": "System.Double", "count": 300, "goo": "GH_Number"},
             {"typeName": "Line",   "clr": "Rhino.Geometry.Line", "count": 12, "goo": "GH_Line"} ],
  "samples": [ {"path": "{0;0}", "value": "3.14", "typeName": "Number", "valueLength": 4} ],
  "warnings": [] }
```

- **`types`** is a histogram of what is actually on the wire. One CLR type -> type the input to it. Mixed -> handle it explicitly, or narrow with the user. Do not assume homogeneity.
- **What the script sees is decided by the type hint.** A hinted param hands the script the native type the hint names (`rg.Line`, `str`) -- `isinstance` works. A param with NO hint marshals geometry as **script-doc `System.Guid` references** (strings/numbers pass through) -- there is no dynamic/object hint to fall back to, the registry only offers concrete types. `convert_staged` auto-selects hints for un-hinted inputs from the live wired data when one mappable type flows; on `set_io`, pass hints yourself. Introspection echoes each param's selected `hint` (plus `availableHints` on script params) -- trust that echo, never `typeName` (it reads "Generic Data" on every script variable regardless of hint).
- **Hint tokens are .NET-style names**, from the component's own registry: `string`, `double`, `int`, `bool`, `Line`, `Curve`, `Point3d`, `Brep`, ... -- NEVER Python names (`str` and `float` do not exist). A wrong token fails loudly listing the real ones; that exception's list is authoritative.
- **When you meet `System.Guid` items** (a mixed tree, an un-hinted legacy component): they are references into the SCRIPT's doc. Dereference via `import scriptcontext as sc; obj = sc.doc.Objects.FindId(g)` or `import rhinoscriptsyntax as rs; ln = rs.coerceline(g)` -- NEVER `Rhino.RhinoDoc.ActiveDoc` (wrong document; `Find` there returns nothing). Caveat, live-confirmed: `rs.coerce*(x, False)` can still THROW on non-geometry input despite `raise_on_error=False` -- route non-geometry (e.g. `isinstance(x, str)`) away first and wrap the coerce in try/except. If a MEMORY lesson says Guids are unresolvable, re-verify with one probe first -- earlier sessions only ever checked the wrong doc.
- **`tree`** decides access: `pathCount == 1` + `isFlat`, many items -> **list** (or **item** for a single value); `pathCount > 1` -> **tree**.
- **`samples`** are ground truth for shape, units, and range -- catch radians-vs-degrees, mm-vs-m, empty branches, and nulls before writing logic.
- **`valueLength` is the full length; `value` itself may be capped** for transport (long values cut at ~2k chars with a trailing ellipsis).
- **`warnings` is data health** -- e.g. a text value at exactly 32767 chars (upstream panel clip; see Big payloads). Repeat a warning to the user plainly before building on that data.
- Values are valid only **after a solve** -- and re-calling `get_document_summary`/`read_input_data` alone NEVER refreshes unsolved data (live-confirmed: repeated reads return the same empty preview). Wireify's own mutations solve by default (`wire`, `convert_staged`, `set_source`), so their follow-up reads are live; if data still looks stale or empty (e.g. after `solve: false`, or a canvas change that has not recomputed), `run` once, then read.

## Data trees

- Choose access deliberately: **item** (one value), **list** (one branch), **tree** (many branches). Wrong access is a top cause of red components and silent data loss.
- **Preserve tree structure** unless the task explicitly wants it flattened or grafted. Silently flattening a tree destroys branch information the rest of the definition depends on.
- For tree access, iterate branches by path and keep input/output paths aligned unless deliberately restructuring -- and when you restructure, do it explicitly in code and say so.
- **Mixed-type trees** (e.g. an Entwine merging lines and labels into ONE input): no single concrete hint can fit -- hinting the whole param to one branch's type fails the solve on the other branch (`ParamConvertException`), and un-hinted, the geometry branch arrives as script-doc Guids. `convert_staged` puts exactly this in its result `warnings` -- **relay it to the user before building on that input**, then either (a) propose wiring each type into its own staged input (usually a free `in2` exists) with one concrete hint each, or (b) keep the wiring and dereference the Guids in-script (`sc.doc.Objects.FindId` / `rs.coerceline`), dispatching per branch.
- **Tree access API:** a `tree` input is a `Grasshopper.DataTree` -- iterate `for path in x.Paths: branch = x.Branch(path)`. There is NO `.PathCount`; `len(x.Paths)` gives the branch count.
- **Tree OUTPUTS from a script:** declare the output `access: "tree"` and assign a real `Grasshopper.DataTree[object]()` built with `.Add(item, GH_Path(i))` directly to the output variable -- no wrapping needed. Ship a companion index-to-label list (branch paths carry no human label), and verify branching from the report's output tree shape (`pathCount` / `dataCount`) -- samples alone can look deceptively uniform.
- **Unit-suffixed value strings** ("530.54 ft") may MIX units per field within one file (coordinates in ft, section dimensions in in) -- parse the suffix per value, never hardcode one unit for the file.

## Big payloads (large JSON, CSV, long text)

Megabyte-scale text does not belong on canvas wires: GH panels clip pasted text, and huge strings make the canvas crawl.

- A `valueLength` of **exactly 32767** means the data was truncated UPSTREAM (the panel paste clip) before Wireify ever saw it -- the read payload's `warnings` says so, and the socket itself shows an orange warning. Say it plainly and stop -- a parse error deep in the content (e.g. `json.loads` failing near char 32767) is the downstream symptom, not a data bug to debug.
- Two supported patterns, both live-validated -- **path-first is the rule**:
  - **File path over the wire (the FIRST choice whenever a path is obtainable)**: the PATH goes into a panel (a short string -- a panel holds it fine) wired to the script's input, and the script opens it at solve time -- `data = json.load(open(path))`. No `Read File` component, no fan-out from a shared node some other branch may quietly depend on. Needs the file readable from the script.
  - **Read File, list access -- ONLY for content that exists solely inside GH** (pasted panels with no file behind them): a stock `Read File` component wired in per-line list mode gives the script one string per file line; join and parse in-script -- `data = json.loads("\n".join(in1))`. Validated on an 80k-line / 2 MB JSON with zero truncation (no single line approaches the clip).
- **Scripts that parse large text should open with the clip guard**, so the failure stays plain-language for anyone who ever opens the file -- with or without Wireify installed:
  ```python
  if isinstance(in1, str) and len(in1) == 32767:
      raise ValueError("in1 is exactly 32767 chars - clipped upstream (GH panel paste limit); wire a file path instead")
  ```
- If the content exists only inside the canvas (no file), ask the user to save it to one; never try to reassemble truncated content.
- **The bypass can be completed tool-side**: `set_panel_text` puts the file path into a panel, `wire` connects the panel (floating params wire with index 0) straight into the socket/component input, and the script opens the path -- the `Read File` leg only enters when the content has no file behind it. Rewiring a user's graph and overwriting a panel are real mutations -- state the plan and get a yes first.

## Dual-runtime correctness (the wedge)

Two runtimes, not interchangeable. `get_runtime_info` shows what is available; `runtime` on `create_python_component` selects it.

**Runtime preflight, once per session, BEFORE the first create/convert:** check `get_runtime_info`. If `cpython3` is not in the available runtimes, STOP and tell the user plainly (their Rhino/RhinoCode install is the issue -- do not retry or improvise around it). If it is available but `rhinoCodeLoaded` is false, warn the user the first Python-3 component load can take a moment (RhinoCode initialises lazily; on some machines it is fragile) -- then proceed. Never spam creates against a runtime that is not there.

**CPython 3** (Rhino 8 SR18+, the default -- prefer it): real Python 3 (f-strings, `range`, true division, `except E as e:`, `print(...)`). Imports `import Rhino.Geometry as rg`, `import rhinoscriptsyntax as rs`, `import Grasshopper`, `import ghpythonlib.components as ghcomp`. `set_source` auto-prepends `#! python 3` -- required; without it the component silently loses its language spec and fails at solve.

**IronPython 2** (Rhino 7, or legacy GhPython on Rhino 8): Python 2.7 on .NET -- **no f-strings**, `xrange`, `print` statement (or `from __future__ import print_function`), integer `/` floor division, `except E, e:`. No `#! python 3` directive. .NET interop via `clr`.

**Never mix.** No f-strings in IronPython 2; no Python-2 `print` statement or `except E, e:` in CPython 3. Unsure which a snippet targets? Stop and check `get_runtime_info` -- a mismatch is a guaranteed red component. For exact API signatures in either runtime, consult `scripting-reference`.

To **modernise an IronPython 2 component to CPython 3**, use the `wireify-port` skill: read the old code, introspect its live inputs, regenerate as typed CPython 3, run both in parallel, diff outputs, fix until equivalent.

## Conventions the loop must get right

- **`# r:` pip header (CPython 3 only).** To use a pip package in a Rhino 8 CPython 3 component, declare it near the top: `# r: numpy` (or pinned, `# r: numpy==1.26`), one requirement per line. Rhino installs it on first run. Rhino 8 also honors `# requirements: <pkg>` (live-verified; the vendored reference uses it) -- both work, `# r:` is the house syntax. Never use either in IronPython 2.
- **`out` is reserved (Rhino 8 CPython 3).** Every script component carries the stdout `out` output by design; `print(...)` lands there. Assigning `out = ...` directly does NOTHING -- it silently yields an empty output with no error. Never declare `out` in your specs or assign it; name your own outputs and `print()` for anything that belongs on `out`.
- **Typed I/O setup.** For every input and output set name, **access (item / list / tree)**, and a type hint where it sharpens correctness -- matched to what `read_input_data` reported. A typed input gives clean Python objects instead of generic goo; the right access prevents silent data-tree loss. Keep output access consistent with what you produce (a list output needs list access).

## Running and fixing

- **The runtime report comes to you.** `convert_staged`, `set_source`, and `run` return it (messages + fresh output values); a separate `read_runtime_errors` is only for re-checking without a solve or for `includeDocument` sweeps.
- The report is the truth: `Error` = it failed; `Warning`/`Remark` = ran with caveats. Read the message literally and fix the specific cause -- wrong access, a runtime-idiom mismatch, an unhandled null/empty branch, a units/tolerance mismatch, a missing import or `# r:` line.
- **An empty-but-valid report with no error** (zero branches, no messages) from `run`/`read_runtime_errors` can mean the component is DISABLED on the canvas -- that state is not exposed by the tools today, so it is invisible to you. Check with the user (or ask them to glance at the component) before treating it as a data or tool failure.
- `run` is a **Task**: it returns a handle; poll for completion, cancel a runaway. Reach for it when you passed `solve: false` (heavy canvas) or need a re-solve without a source change.
- `set_source` is idempotent -- fix in place on the same component; never spawn a duplicate component to try a variant.

## Memory and conventions

This project's `CLAUDE.md` and the shared `~/.ify/wireify/defaults.md` carry standing conventions -- units, tolerance, go-to libraries, naming, and (where set) structural/AEC semantics. Honour them.

`MEMORY.md` at the home root is this definition's lesson ledger. **Read it at session start** (the loop's orient step) -- it is the prior context here, and it is NOT the same file as Claude Code's auto-memory (`~/.claude/projects/.../memory/MEMORY.md`), which nothing in a Wireify home writes. When the user asks what you know or remember about this definition, the answer comes from reading `./MEMORY.md` -- never report "memory is empty" without having read it. After a non-obvious fix, append a lesson there as a dated `### ` entry per the ledger's format rules (top of the file), then read the file's tail back once to confirm the append landed.

A ledger lesson records what was observed THEN. When one contradicts this skill on tool mechanics (what a tool returns, how data marshals), re-verify live with one cheap probe before trusting either -- the plugin changes between builds, and a stale lesson repeated confidently is worse than no lesson. Update the ledger entry when a re-check disproves it.

**Missing memory after a rename or move?** Wireify adopts a renamed/moved definition's old home automatically when it can identify it exactly. When it cannot (ambiguity, or no confident match), it records the unmatched orphaned homes in `.wireify/adoption-candidates.json` at this home's root. If the user says lessons are missing: Read that file, propose the most plausible candidate from its entries (recorded path, last connect, ledger size), and ONLY with the user's explicit confirmation merge that home's `MEMORY.md` lessons into this ledger (append below the header rules, keeping the entry format; never overwrite this ledger, never modify the original home). No file, or no plausible candidate -- say so plainly; never graft a ledger on a guess.

## Tool reference (this project's `wireify` server)

- Orient (read-only, batchable): `get_document_summary` (the `wireify` numbered registry; `includeStagedData: true` inlines staged input data), `introspect_selected`, `introspect_component` (components AND floating params -- a panel or slider reports as its own single output; every param carries its LIVE wiring as `sources`/`recipients` -- the is-this-spare check), `read_input_data`, `get_runtime_info`, `get_source` (read an existing script component's code).
- Build (one at a time, each returns its own verification): `convert_staged` (socket -> stock Python component, explicit I/O, wires kept, + first solve's report), `create_python_component`, `set_io` (explicit I/O for plain script-mode), `set_source` (recompile + solve + report; `solve: false` to defer; refuses with `WIREIFY_EXTERNAL_EDIT` when the code was hand-edited outside Wireify -- merge, then retry), `wire` (one undo step, solves after wiring; STRICT by default -- an occupied input refuses, pass mode `replace` or `add` deliberately; either end may be a floating param -- index 0), `set_panel_text` (write text into an existing Panel, one undo step -- see Canvas etiquette); `set_typed_io` (SDK-mode `RunScript` sync only); `delete_component` (Wireify sockets + script components only, one undo step -- see Canvas etiquette).
- Run / re-check: `run` (Task, returns the report; it RE-SOLVES, so the front canvas is required, and `runCount: -1` on natives/params is normal), `read_runtime_errors` (messages + current output values WITHOUT solving -- background tab, native components, and floating params included; `includeDocument` for the whole canvas).
